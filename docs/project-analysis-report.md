# FluffCatch 项目架构与工程质量分析报告

> 分析日期：2026-07-15  
> 分析范围：Go 后端、React 前端、数据库迁移、对象存储、配置、认证、测试、构建与发布流程。  
> 验证方式：静态源码分析，并执行 `go test ./...`、`go test -race ./...`、`go vet ./...` 和 `npm run build`。

## 1. 总体结论

FluffCatch 是一个面向活动返图收集、审核和展示场景的自部署应用，采用“Go 单体后端 + React SPA + 关系数据库 + 对象存储”架构。功能链路完整，部署简单，对象存储抽象较成熟，适合单实例、中小规模活动使用。

当前架构成熟度可概括为：

| 维度 | 评价 | 说明 |
| --- | ---: | --- |
| 功能完整度 | 8/10 | 投稿、审核、画廊、私密访问、点赞、存储策略均已闭环 |
| 模块划分 | 7/10 | 领域包清晰，但 HTTP 层和 GORM 仍有明显穿透 |
| 数据一致性 | 4/10 | 数据库与对象存储之间依赖脆弱的补偿删除 |
| 可扩展性 | 4/10 | Session、验证码、限流等均为进程内状态 |
| 安全性 | 5/10 | 基础认证设计合理，但存在明文口令、秘密落盘和限流缺口 |
| 测试保障 | 4/10 | 基础包有测试，核心业务和前端覆盖严重不足 |
| 运维能力 | 4/10 | 缺少完整 readiness、指标、审计日志、备份恢复和持续集成 |

## 2. 系统定位与技术栈

FluffCatch 的核心业务流程为：

1. 管理员创建活动并配置时间、地点、封面、公开状态和私密访问口令。
2. 管理员生成限时投稿链接，可限制有效期、使用次数并绑定摄影师名称。
3. 投稿者匿名或署名上传图片和视频，文件进入待审核池。
4. 管理员审核投稿，选择公开或私密可见性。
5. 访客浏览画廊、筛选、点赞、下载公开内容，并通过口令访问私密内容。

主要技术栈：

- 后端：Go 1.25、Gin、GORM。
- 数据库：默认 SQLite，也支持 MySQL。
- 前端：React 19、TypeScript 6、Vite 8、MUI 9、React Router 7。
- 对象存储：本地文件系统、AWS S3、MinIO、Cloudflare R2、阿里云 OSS、腾讯云 COS 和通用 S3。
- 认证：PBKDF2-SHA256 管理员密码、内存 Session、验证码、可选 OIDC。
- 媒体处理：标准库图片解码、自实现 EXIF/TIFF/ISO-BMFF 解析、缩略图和模糊预览。
- 发布：Vite 构建产物可通过 `embed_frontend` 编译标签嵌入 Go 二进制。

## 3. 总体架构

```text
浏览器 React SPA
      |
      | Cookie / JSON / Multipart
      v
Gin HTTP 路由与 Handler
      |
      +--> auth       管理员认证、验证码、Session
      +--> events     活动管理
      +--> uploads    投稿、上传、审核
      +--> gallery    画廊、标签、点赞、访问控制
      +--> settings   动态站点与存储设置
      |
      +--> GORM ------> SQLite / MySQL
      |
      +--> Store -----> 本地 / S3 / MinIO / OSS / COS / R2
```

应用入口位于 `cmd/fluffcatch/main.go`，负责：

1. 解析迁移、密码重置、EXIF 回填和前端模式等 CLI 参数。
2. 按“内置默认值 < YAML < 环境变量”加载配置。
3. 打开数据库，并在新 SQLite 数据库上执行初始迁移。
4. 自动生成并写回 Session 密钥和管理员密码哈希。
5. 从数据库 `settings` 表加载动态站点、上传和存储设置。
6. 构造存储 Manager、领域 Service 和 HTTP Server。
7. 启动 HTTP 服务并处理 SIGINT/SIGTERM 优雅关闭。

前端入口位于 `www/src/main.tsx`，根组件挂载主题、BrowserRouter、错误边界和懒加载路由。前端既可由 Vite 独立运行，也可编译进单个 Go 可执行文件。

## 4. 目录与模块职责

| 目录 | 职责 |
| --- | --- |
| `cmd/fluffcatch/` | CLI、依赖装配、进程生命周期、迁移和离线任务入口 |
| `internal/http/` | 路由、认证边界、请求校验、限流、业务编排、媒体与 SPA 服务 |
| `internal/events/` | 活动 CRUD、公开过滤、封面引用和活动删除前对象清单 |
| `internal/uploads/` | 投稿链接、上传检测、对象写入、投稿审核转换 |
| `internal/gallery/` | 画廊查询、标签、可见性、点赞和媒体访问判定 |
| `internal/settings/` | 数据库动态设置、规范化和存储策略引用检查 |
| `internal/storage/` | `Store` 接口、多策略 Manager 和云存储适配器 |
| `internal/auth/` | 管理员密码、Session、验证码和认证模型 |
| `internal/image/` | EXIF、缩略图、背景裁切和模糊预览 |
| `internal/tasks/` | EXIF 回填等离线任务 |
| `migrations/` | MySQL 与 SQLite 初始化结构和嵌入式迁移 |
| `www/src/` | React 页面、布局、组件、主题和 API 客户端 |

目录划分总体合理，领域包之间不存在源码级循环依赖。主要问题不是依赖环，而是 `internal/http`、GORM 模型和前端 API 客户端的扇入、扇出过大。

## 5. 核心数据模型

主要实体位于 `internal/db/models.go`：

- `Event`：活动信息、封面对象、公开状态、投稿开关和私密口令。
- `Submission`：待审核文件、存储策略、SHA-256、标签 JSON、EXIF 和状态。
- `Photo`：正式媒体、公开或私密可见性、点赞冗余计数、标签和拍摄时间。
- `SubmissionLink`：投稿 token 哈希、有效期、最大次数和使用次数。
- `Tag`、`PhotoTag`：全局标签及照片标签多对多关系。
- `PhotoLike`：照片与访客指纹哈希的联合主键关系。
- `Setting`：站点、上传和存储策略的 JSON 设置。

重要约束：

- 同一活动内，`photos` 和 `submissions` 分别对 `(event_id, content_hash)` 建立唯一约束。
- 投稿 token 只保存 SHA-256 哈希，这是合理的安全设计。
- 点赞通过 `(photo_id, fingerprint_hash)` 去重。
- 活动删除主要依赖数据库外键级联删除业务记录。
- 活动私密口令同时保存 PBKDF2 哈希和明文，这是明显的敏感数据风险。

## 6. 核心业务调用链

### 6.1 访客投稿

```text
投稿 Token 预校验
→ Multipart 文件落临时文件
→ MIME 嗅探、SHA-256 和重复检测
→ 获取当前活动存储策略
→ 写入原始对象
→ 提取 EXIF 并生成缩略图
→ 数据库事务锁定并消费 Token 次数
→ 创建 Submission
→ 数据库失败时补偿删除对象
```

管理员也可以使用同一上传端点，但会调用直接批准路径创建 `Photo`，并跳过活动投稿开关。

该流程的优点是校验完整、对象存储策略清晰，并对数据库失败进行了补偿。缺点是对象存储和数据库不存在真正的原子事务，补偿逻辑无法覆盖并发和删除失败。

### 6.2 投稿审核

审核通过时，系统在数据库事务中：

1. 读取待审核 Submission。
2. 创建正式 Photo。
3. 创建或复用标签并挂接 PhotoTag。
4. 删除 Submission。

对象键和存储策略保持不变，不发生对象复制，因此审核操作成本较低。

### 6.3 公开与私密画廊

画廊服务负责：

- 检查活动是否公开。
- 按公开或私密可见性筛选。
- 应用分页、标签、摄影师、媒体类型和排序条件。
- 附加当前访客的点赞状态。
- 根据权限生成原图、缩略图或模糊预览 URL。

私密口令验证成功后，后端设置按活动隔离的 HMAC Cookie。媒体请求仍会在服务端重新执行访问判定，而不是仅依赖前端隐藏，安全边界方向正确。

### 6.4 点赞

后端为浏览器创建随机访客标识，数据库只保存其 SHA-256 指纹。点赞事务先尝试插入 `PhotoLike`，成功后再递增 `Photo.like_count`。这是典型的去重记录加冗余计数设计。

### 6.5 设置热更新

后台设置写入数据库 `settings` 表。存储设置更新后，`storage.Manager.Reconfigure` 构建新的 Store 映射，并通过锁替换运行态配置。

已有媒体始终按记录中的 `storage_policy_id` 读取旧 Store；切换 active policy 只影响新对象。删除仍被引用的策略会被引用检查器拒绝，这一设计较合理。

## 7. 设计模式与架构优点

项目中可以识别出以下模式：

- Service Layer：events、uploads、gallery 封装领域规则和事务。
- Strategy + Adapter：统一 `storage.Store` 接口适配不同对象存储。
- Manager/Registry：`storage.Manager` 维护 policy 到 Store 的映射并支持热重配。
- Repository：settings 使用独立 Store 隔离 JSON 设置持久化，但其他领域尚未建立同等边界。
- Compensating Transaction：对象先写、数据库失败后删除对象。
- Optimistic UI：点赞先更新前端状态，失败时回滚。
- SPA + Server Shell：后端提供 SPA fallback，并动态处理部分 SEO 元信息。

值得肯定的部分：

- 单二进制部署简单，适合自托管场景。
- 对象存储适配接口紧凑，扩展新存储驱动成本较低。
- 每条媒体记录保存自己的策略 ID，避免切换存储后旧数据失联。
- 投稿 token 只保存哈希。
- 私密媒体在服务端执行二次鉴权。
- JSON 请求拒绝未知字段，降低错误配置和协议漂移风险。
- SQLite 启用 WAL、外键和 busy timeout，并限制为单连接以降低锁冲突。

## 8. 模块耦合度评估

| 关系 | 耦合度 | 评价 |
| --- | ---: | --- |
| HTTP → 领域服务 | 高 | `Server` 集中持有大量服务、缓存、限流器和运行态对象 |
| 领域服务 → GORM | 很高 | events、gallery、uploads 直接依赖 `*gorm.DB` 和数据库模型 |
| HTTP → GORM | 高 | 部分后台 handler 绕过服务直接操作数据库 |
| 业务 → 对象存储 | 中 | 有统一 `Store` 接口，但业务依赖具体 `storage.Manager` |
| 配置 → 运行时 | 很高 | YAML、环境变量、数据库 settings 和启动快照同时存在 |
| 前端 → API | 高 | DTO、缓存和约 50 个端点集中在单个 `client.ts` |
| 外部云服务 | 中高 | SDK 直接实例化，缺少统一超时、重试和监控接口 |

### 8.1 对象存储边界

对象存储是项目中最成熟的模块边界。`Store` 只暴露 `Put`、`Get`、`Delete` 和 `PublicURL`，业务逻辑无需理解具体云 SDK。

不足之处是业务层依赖具体 `*storage.Manager`，而不是更小的策略解析接口；各云客户端的超时、重试、取消和可观测能力也不一致。

### 8.2 数据库边界

数据库是当前最弱的边界：

- 领域服务直接操作 GORM。
- 领域对象与数据库模型基本重合。
- SQL 表名和方言进入业务代码。
- 部分 HTTP handler 直接访问数据库。
- SQLite 和 MySQL 兼容逻辑分散在连接层、迁移和服务层。

这不会妨碍当前单体开发，但会显著提高替换 ORM、拆分服务、维护双数据库或进行隔离测试的成本。

### 8.3 配置耦合

项目同时存在四类配置来源：

1. 代码内置默认值。
2. YAML 文件。
3. 环境变量。
4. 数据库 `settings` 表。

此外，`Server.cfg` 保存启动快照，部分 handler 动态读取数据库设置，部分仍读取启动配置。同一个上传限制或存储概念可能出现不同的运行结果，形成多个事实来源。

### 8.4 前端耦合

前端没有 Redux、MobX 或 React Query，页面主要通过局部 `useState/useEffect` 管理请求。对于当前规模这是务实选择。

主要问题是：

- `www/src/api/client.ts` 同时承担 DTO、HTTP 请求、缓存、失效和所有 API 函数。
- `EventDetailPage` 同时承担公开和私密列表、筛选、分页、点赞、管理、选择和下载。
- API 地址固定为同源相对路径，独立域部署缺少明确 API base URL 和 CORS 边界。

## 9. 关键风险

### 9.1 严重：并发相同文件上传可能删除成功对象

上传流程先查询重复，再按内容哈希生成固定对象 key，最后才插入数据库。两个相同文件的并发请求可能同时通过查重并写入同一个 key。

数据库唯一约束会使其中一个事务失败。失败请求随后无条件执行补偿删除，从而删除另一个成功事务正在引用的对象，最终形成“数据库记录存在，但媒体文件丢失”。

这是当前优先级最高的数据正确性问题。

### 9.2 高：SQLite 与 MySQL 方言混用

点赞和照片标签关联使用 GORM `clause.Insert{Modifier: "IGNORE"}`，会生成 MySQL 风格 `INSERT IGNORE`。默认数据库是 SQLite，而 SQLite 不支持这一语法。

因此默认 SQLite 下点赞、标签更新或投稿审核可能失败。现有 SQLite 测试仅覆盖数据库初始化，没有覆盖这些领域路径。

### 9.3 高：数据库与对象存储没有可靠事务

不同操作采用不同顺序：

- 上传：先写对象，后写数据库，失败后补偿删除对象。
- 删除正式媒体：先删数据库，后尽力删除对象。
- 删除投稿：先删除对象，后删除数据库记录。

可能产生：

- 孤儿对象。
- 数据库记录指向不存在的对象。
- 部分成功且无法准确重试。
- 返回结果与实际状态不一致。

维护扫描接口能够发现部分问题，但不能提供一致性保证。

### 9.4 高：存储配置持久态与运行态分裂

存储设置更新顺序是：

1. 写入数据库。
2. 调用 `storage.Manager.Reconfigure`。

如果第二步失败，请求返回错误，但错误配置已经持久化，当前进程仍运行旧配置。下次重启时，应用可能因无法构建持久化的存储策略而启动失败。

### 9.5 高：活动私密口令明文持久化

`Event` 同时保存 `private_password_hash` 和 `private_password_plain`，管理员 API 还会返回明文。

这意味着数据库备份、只读数据库账号、管理员会话或 API 日志泄露后，所有活动口令都会直接暴露。如果产品不要求恢复原口令，应只保存哈希，并提供重置而不是查看功能。

### 9.6 高：上传内存与超时设计冲突

动态设置允许：

- 图片最高 1 GiB。
- 视频最高 10 GiB。
- 最多 8 个并发上传。

图片虽先写入临时文件，但随后会被完整 `io.ReadAll`，再进行 EXIF、图片解码、缩略图和 JPEG 编码。多个大图片请求可能造成数 GiB 内存峰值和大量临时磁盘 I/O。

同时 HTTP 默认 `ReadTimeout` 只有 10 秒，`WriteTimeout` 只有 30 秒，与大文件上传和下载场景明显冲突。

### 9.7 高：进程内状态阻碍水平扩容

以下状态均保存在单进程内存：

- 管理员 Session。
- 验证码。
- OIDC state/nonce。
- 登录、验证码和活动列表限流。
- 模糊预览缓存。

结果包括：

- 重启导致管理员全部退出。
- 重启中断正在进行的验证码和 OIDC 流程。
- 多实例之间认证和限流状态不一致。
- 水平扩容必须依赖粘性会话。

### 9.8 中高：私密口令接口没有独立限流

私密口令验证会执行高成本 PBKDF2，但对应接口没有独立限流。攻击者既可以在线猜测弱口令，也可以用大量错误请求制造 CPU 压力。

### 9.9 中高：迁移不具备原子性

迁移 SQL 被拆成多条后逐条执行，全部成功后才写入 `schema_migrations`。如果中途失败，会留下部分结构但不记录版本；后续重试可能因对象已经存在而再次失败。

### 9.10 中：健康检查不能作为 readiness

数据库未连接或 Ping 失败时，健康接口仍返回 HTTP 200，顶层 `status` 仍为 `ok`。接口也没有验证当前活动对象存储是否可用。

因此负载均衡器或 Kubernetes readiness probe 无法依据该接口摘除故障实例。

### 9.11 中：活动列表存在 N+1 查询

活动列表先查询活动集合，再为每个活动单独统计照片数量。默认单页 24 个活动时至少产生额外 24 次 Count 查询。

可以通过聚合子查询或一次 `GROUP BY event_id` 消除该问题。

### 9.12 中：批量操作语义不清晰

批量上传在前几个文件成功、后续文件失败时直接返回错误，不回滚已创建内容。批量审核和删除则把逐项错误拼入 message，但整体仍返回 nil error 和 HTTP 200。

调用方难以稳定判断完全成功、部分成功或完全失败，建议返回结构化逐项结果。

### 9.13 中：限流实现与代理策略存在问题

`rateLimiter.perSec` 字段没有实际参与算法，真实行为是“一秒窗口内最多 burst 次”。不同接口获取客户端地址的方式也不一致：部分只看 `RemoteAddr`，部分信任 `X-Forwarded-For`。

反向代理部署后可能出现所有用户共享额度，或通过伪造转发头绕过限流。

### 9.14 中：部分媒体格式无法生成缩略图

上传允许 WebP、HEIC、HEIF 和 AVIF，但当前标准库解码器只注册 GIF、PNG 和 JPEG。允许上传不代表能够生成缩略图；失败会被弱化处理，最终导致部分媒体缺少预览。

## 10. 安全分析

### 10.1 已有安全措施

- 管理员密码采用 PBKDF2-SHA256。
- Session Cookie 使用 HttpOnly 和 SameSite。
- 投稿 token 只保存哈希。
- 登录和部分高风险操作需要验证码。
- 私密画廊通过签名 Cookie 保存授权。
- 私密媒体在服务端执行访问控制。
- JSON 解码拒绝未知字段。
- 本地存储实现包含路径安全检查。

### 10.2 主要安全缺口

- 活动私密口令以明文保存。
- 本地 `config.yaml` 包含数据库、Session 和 OIDC 等敏感配置。
- OIDC 绑定和解绑会把完整 OIDC 配置写回 YAML，包括可能来自环境变量的 client secret。
- 缺少统一 CSRF token 或 Origin 校验。
- 缺少 CSP、HSTS、`X-Content-Type-Options` 和 `Referrer-Policy` 等响应头。
- 投稿 token 出现在查询字符串中，可能进入浏览器历史、代理日志和监控系统。
- OIDC 回调和跳转地址依赖请求 Host、Forwarded、Origin 或 Referer，缺少显式外部基础 URL。
- 缺少结构化安全审计日志。

建议把敏感配置交给环境变量或专用 Secret 管理系统，配置写回操作只修改真正需要持久化的绑定 subject。

## 11. 性能与容量

主要性能热点：

- 图片处理在 HTTP 请求线程同步完成。
- 大图片被完整读入内存并产生多个中间副本。
- SQLite 被固定为单数据库连接，高并发写入会串行等待。
- 活动列表存在照片 Count N+1。
- EXIF 回填一次加载全部候选记录，并完整读取每个原图。
- 浏览器批量 ZIP 下载会同时保留源文件和最终 ZIP，可能耗尽标签页内存。
- 模糊预览缓存位于单进程内存，容量固定且没有跨实例复用。

SQLite 单连接对小规模部署是合理的稳定性取舍，但高并发上传、审核和点赞场景应使用 MySQL，并补充真实压力测试。

## 12. 外部服务依赖与故障面

| 外部依赖 | 必需性 | 故障影响 | 当前隔离程度 |
| --- | --- | --- | --- |
| SQLite/MySQL | 必需 | 核心 API 基本不可用 | 低，业务直接依赖 GORM |
| 本地或云对象存储 | 必需 | 上传和媒体读取失败 | 中，有 `Store` 接口 |
| OIDC Provider | 可选 | OIDC 登录或绑定失败 | 低，HTTP client/provider 不可注入 |
| npm/Go 模块源 | 构建期 | 无法构建发布 | 中，有锁文件和 go.sum |

应用启动采用全量 fail-fast：数据库、配置写回、动态设置加载或任一存储策略初始化失败都会终止进程。目前没有只读降级模式、后台重连或存储策略隔离启动机制。

## 13. 前端架构与构建体积

前端按路由懒加载，公共布局与后台布局分离。API 客户端实现短 TTL GET 缓存、并发请求去重和标签失效。

## 15. 运维与可观测性

当前运维能力较弱：

- 生产模式缺少结构化访问日志。
- 没有请求 ID、统一耗时和状态码日志。
- 没有 Prometheus 指标或追踪。
- 没有错误率、上传失败、存储延迟和数据库锁等待指标。
- 没有 Dockerfile、systemd 或 Kubernetes 示例。
- 没有备份恢复、日志轮转、容量规划和灾难恢复文档。
- SessionStore 和限流器提供 `Stop`，但进程关闭时没有调用，重复创建 Server 时可能泄漏 goroutine。

建议优先建设：

1. 分离 liveness 和 readiness。
2. 增加请求 ID 和结构化访问日志。
3. 增加数据库、对象存储、上传和审核指标。
4. 编写 SQLite 文件与对象存储联合备份恢复流程。
5. 明确单实例与多实例部署约束。

## 16. 整改路线

### P0：数据正确性与安全

- 修复相同内容并发上传的补偿删除竞态。
- 将 `INSERT IGNORE` 替换为跨方言 `OnConflict DoNothing`。
- 停止保存和返回活动私密口令明文。
- 轮换并隔离本地配置中的数据库、OIDC 和 Session 密钥。
- OIDC 绑定写回时只保存 `bound_subject`。

### P1：一致性与测试

- 为对象写入和删除建立操作状态或 outbox。
- 增加幂等删除、重试和定期孤儿清理任务。
- 存储配置改为“先构建验证、再持久化、最后原子切换”。
- 建立 SQLite/MySQL 集成测试矩阵。
- 覆盖上传并发、Token 次数竞争、点赞、标签和批量部分失败。
- 使数据库迁移在事务中执行，或为不可事务 DDL 提供可恢复策略。

### P2：安全、容量与运维

- 为私密口令接口增加独立限流。
- 明确可信代理和外部基础 URL。
- 添加安全响应头和统一 Origin/CSRF 防护。
- 限制图片实际解码资源，避免大文件整体读入内存。
- 为上传和下载设计独立超时或流式端点。
- 完善 readiness、结构化日志、指标和备份恢复文档。
- 建立 PR CI：test、race、vet、前端测试、构建和依赖扫描。

### P3：架构演进

- 为 Session、验证码、OIDC state 和限流建立可替换 Store 接口。
- 多实例部署前引入 Redis 或等价共享状态服务。
- 为 events、gallery、uploads 逐步建立 repository 边界。
- 将前端 API 客户端按领域拆分。
- 拆分职责过重的 `EventDetailPage` 和后台设置页面。
- 为云存储客户端统一超时、重试、Context 和可观测接口。

## 17. 最终判断

FluffCatch 当前适合作为单实例、中小流量的自部署返图系统。功能设计和部署体验已经形成完整产品闭环，对象存储策略也是一个质量较高的扩展点。

在承载重要活动数据或扩大并发前，应优先解决以下四类问题：

1. 并发上传导致的对象误删除。
2. SQLite 与 MySQL 方言不兼容。
3. 活动私密口令明文保存。
4. 数据库与对象存储跨资源一致性不足。

项目当前不需要直接拆分微服务。更合适的演进方向是继续保持模块化单体，通过可靠事务边界、共享状态抽象、集成测试和可观测性，提高数据正确性与运行稳定性。
